# Архитектура ядра Sora

Документ описывает `core` — привилегированное сетевое ядро, которое обслуживает
приложение на Windows, Linux, Android и Android TV. Он написан для двух читателей:
для того, кто меняет код, и для того, кто ревьюит изменение. Дата проверки кода:
**02.10.2026**, ветка `feat/core-control-plane`.

## 1. Что обязано быть правдой

Четыре утверждения, ради которых существует ядро. Каждое проверяется тестом, и
нарушение любого из них считается дефектом, а не стилем.

1. **Интерфейс не получает секретов.** План сессии несёт ссылки, а не значения.
   Ядро разрешает ссылки в своём хранилище и никогда не отдаёт материал обратно.
2. **Ядро не забывает систему.** Всё, что ядро меняет в системе, оно меняет
   через guard и восстанавливает на каждом пути выхода, включая падение движка и
   остановку службы.
3. **Ядро не лжёт о состоянии.** Журнал событий монотонен, состояние сессии
   меняется только по таблице переходов, а клиент, пропустивший события, всегда
   может прийти за снимком состояния.
4. **Ядро не печатает то, что нельзя печатать.** Ошибки, логи движка и
   диагностические архивы проходят через маскирование; адреса серверов, UUID,
   пароли, пути и имена хостов не покидают процесс.

## 2. Слои

```
                 interface (Flutter, непривилегированный)
                                  |  gRPC: sora.core.v1, именованный канал или сокет
                                  v
+----------------------------------------------------------------------+
| core/control   перевод контракта: версии, лимиты, коды ошибок, поток  |
+----------------------------------------------------------------------+
| core/session   состояние сессии, супервизор, журнал событий, guard    |
+----------------------------------------------------------------------+
| core/parser    разбор подписок и ссылок в engine.Plan                |
| core/probe     проверка серверов                                     |
| core/subscription  загрузка подписки                                 |
| core/diagnostics   отчёт и безопасный архив                          |
+----------------------------------------------------------------------+
| core/secret    шифрованное хранилище материалов (AES-256-GCM, DPAPI)  |
| core/errs      каталог ошибок: код, ключ локализации, деталь          |
+----------------------------------------------------------------------+
| core/engine    план, движок, маскирование, backoff, бюджет рестартов  |
| core/engine/mihomo  дочерний процесс и его control API               |
+----------------------------------------------------------------------+
```

Правило зависимостей строгое и однонаправленное: `control` знает о `session`,
`session` знает о `engine`, `engine` ничего не знает о `control`. Каталог ошибок
и хранилище секретов стоят ниже всех и не знают ничего о транспорте, поэтому их
можно использовать и в службе туннеля Android, где gRPC тот же, а окружение
другое.

## 3. Жизненный цикл сессии

```
disconnected --connect--> connecting --ok--> connected
                               |                   |
                               |                   +-- движок упал --> reconnecting
                               |                   |                       |
                               |                   |            +----------+----------+
                               |                   |            v                     v
                               |                   |      connected              failed
                               |                   |
                               +-ошибка--> failed   +--disconnect--> disconnected
```

* `Connect` возвращается, когда туннель поднят или окончательно не поднялся.
  Ошибка, которую имеет смысл повторить, не возвращается ошибкой: сессия уходит
  в `reconnecting` и продолжает работу сама, потому что пользователь не должен
  нажимать «подключиться» дважды.
* Переподключение идёт с backoff (500 мс … 2 мин, с джиттером) внутри бюджета
  рестартов (5 попыток за 10 минут на сессию). Бюджет у каждой сессии свой: иначе
  попытки сессии, упавшей час назад, заблокировали бы следующее подключение.
* Исчерчание бюджета — это `failed`, а не бесконечный цикл. Клиент получает
  `retry_after` в состоянии, а не крутящийся индикатор без срока.
* `Disconnect` идемпотентен и безопасен из трёх мест: команда пользователя,
  выключение службы и аварийный путь супервизора.
* Guard применяется ровно один раз на успешный `Apply` движка и восстанавливается
  ровно один раз. Сессия, которая упала до применения, не трогает систему и не
  удаляет правила чужой программы.

## 4. Границы доверия

| Что | Кто владеет | Кто читает |
| --- | --- | --- |
| Секреты подписки | ядро, шифрованно | ядро |
| План сессии | ядро | ядро |
| Системные настройки (прокси, firewall, tun) | ядро, через guard | ядро |
| Снимок состояния и события | ядро | интерфейс |
| Бинарник движка | установщик | ядро, после проверки |

Интерфейс непривилегирован и может исчезнуть в любой момент. Ни один путь в
ядре не ждёт, что интерфейс останется: сессия живёт на своём контексте, журнал
переживает переподключение клиента, а `Shutdown` возвращает машину в исходное
состояние, даже если клиента уже нет.

## 5. Решения, которые зафиксированы

1. **Движок — дочерний процесс, а не библиотека.** У mihomo нет стабильного
   публичного Go API; управление идёт через его собственный HTTP-контроллер.
   Это оставляет внутренности ядра на волю апстрима и не превращает Sora в
   единое произведение по GPL.
2. **Конфигурация уходит по stdin.** `mihomo -f -` читает конфигурацию из
   стандартного ввода, поэтому пароли не появляются ни в аргументах процесса, ни
   на диске.
3. **Секрет-хранилище — AES-256-GCM, ключ у операционной системы.** На Windows
   ключ обёрнут DPAPI в области пользователя, в остальных системах лежит в файле,
   доступном только владельцу. Идентификатор хранилища связан с шифротекстом как
   additional data, поэтому ключ и хранилище от разных установок нельзя смешать.
4. **Никакого пользовательского текста в ядре.** Ошибка несёт код, ключ
   локализации и деталь; формулировки живут в интерфейсе.
5. **Деталь ошибки собирается ядром, а не копируется из причины.** `url.Error`
   содержит токен подписки, `net.OpError` — адреса, `x509` — имя сервера, а
   некоторые `x509`-ошибки паникуют при печати без сертификата. Ядро строит
   безопасную деталь само.
6. **События не блокируют движок.** Медленный подписчик теряет события, счётчик
   потерь виден клиенту, а восстановление идёт через снимок состояния.
7. **Контракт расширяется только вперёд и только если без этого нельзя.** Добавлены
   `PutSecret` и `DeleteSecret`: без них хранилище секретов нечем наполнить, а
   любой другой способ передать материал превращал бы один из методов в способ
   прочитать чужой секрет.

## 6. Ошибки и маскирование

Ошибка ядра состоит из трёх независимых частей, и смешивать их нельзя:

| Часть | Отвечает на вопрос | Кто её читает |
| --- | --- | --- |
| `Code` | что за класс отказа | транспорт: повторять, ждать, отказать |
| `Key` | что показать пользователю | интерфейс, по своим ресурсам |
| `Detail` | что произошло здесь | оператор в журнале, уже замаскированное |

Правила, которые держит пакет `errs`:

* набор кодов закрыт: новый класс отказа — это изменение контракта;
* ключ локализации никогда не меняет смысл, ключ добавляется, а не переименовывается;
* деталь всегда одна строка: перевод строки в причине не должен породить
  поддельную запись в журнале;
* адрес, имя хоста и локальный путь не попадают в деталь: адрес сервера
  идентифицирует учётную запись у провайдера, а путь — пользователя машины.

## 7. Что ещё предстоит

| Слой | Состояние | Следующий шаг |
| --- | --- | --- |
| `core/errs` | готов | — |
| `core/secret` | готов | ротация мастер-ключа при смене учётной записи |
| `core/session` | готов | реализация guard под Windows и Linux |
| `core/control` | в работе | gRPC-сервер, транспорт, поток событий |
| `core/probe` | не начат | TCP и TLS проверки с ограничением параллелизма |
| `core/subscription` | не начат | загрузка с лимитами, редиректами и кэшем |
| `core/diagnostics` | не начат | отчёт и архив без секретов |
| `service/windows` | пусто | установка, права, автозапуск |
| `service/linux` | пусто | unit-файлы, пользователь, права |
| `app` | скелет | UI вне этой задачи: дизайн не трогаем |

Каждый шаг добавляет тесты раньше, чем код считается готовым, и ни один шаг не
меняет уже опубликованную часть контракта.
