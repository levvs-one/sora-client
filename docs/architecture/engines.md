# Движки Sora

Документ описывает, как ядро Sora запускает сетевые движки mihomo, sing-box и
Xray-core и как выбирает между ними. Дата проверки кода: **06.10.2026**, ветка
`feat/core-engines-unified`. Все утверждения о движках проверены их собственными
валидаторами на сборках mihomo v1.19.32, sing-box v1.14.2 и Xray-core v26.3.27.

## 1. Зачем три движка

Happ построен целиком на Xray (см. `docs/research/competitor-happ.md`, §2). Один
движок — это одна точка отказа: если цензор научился ломать конкретную сборку
или протокол, клиент на одном ядре ломается целиком. Sora держит три движка и для
каждого плана выбирает тот, который способен провести его полностью.

| Что умеет только он | Движок |
| --- | --- |
| XHTTP, VLESS Encryption, REALITY в варианте Xray, балансировщики с observatory | Xray |
| AnyTLS, tun с собственной таблицей маршрутов на всех платформах, наименьшая память, нативная сборка под Android | sing-box |
| AmneziaWG, fallback-группы, proxy-providers, самый полный язык правил, горячая перезагрузка конфигурации | mihomo |

## 2. Слои

```
core/engine            план, матрица возможностей, выбор движка, маскирование
core/engine/registry   какие движки есть на машине; фабрика движка под план
core/engine/supervise  жизнь дочернего процесса: проба, stdin, проверка,
                       handshake, рестарт с backoff в бюджете, остановка
core/engine/clashapi   клиент Clash API и управление для mihomo и sing-box
core/engine/mihomo     драйвер: YAML, аргументы, горячая перезагрузка
core/engine/singbox    драйвер: JSON формата 1.12+
core/engine/xray       драйвер: JSON, метрики, тестер задержки, закрепление выбора
core/engine/enginetest планы, на которых тесты гоняют валидаторы всех движков
```

Движок — это `Driver` (грамматика конфигурации, командная строка, handshake,
горячее применение) плюс управляющая половина (группы, выбор, задержка,
счётчики). Всё остальное общее и живёт в `supervise.Supervisor`. Исправление в
супервизии сразу доходит до всех трёх движков.

## 3. Инварианты, общие для всех движков

1. **Конфигурация уходит только по stdin.** `mihomo -f -`, `sing-box run -c stdin`,
   `xray run -c stdin:`. Пароли не появляются ни в аргументах процесса, ни на диске.
2. **Перед запуском конфигурацию проверяет сам движок.** `mihomo -t`,
   `sing-box check`, `xray run -test`. Ошибку в ключе, которую сделала Sora, ловит
   единственная сторона, знающая грамматику, и ловит до открытия портов.
3. **Контроллер слушает только loopback и всегда с секретом.** Секрет — 32 байта из
   `crypto/rand`, новый на каждый запуск. Исключение — метрики Xray: у expvar нет
   аутентификации, поэтому туда не попадает ничего, кроме счётчиков и тегов
   вида `o0001`. Имена серверов в Xray не передаются.
4. **Окружение дочернего процесса урезано.** Переменные прокси и секреты службы
   движку не передаются.
5. **Вывод движка ограничен и маскируется.** Последние 80 строк хранятся в
   хвосте; в события они попадают только через `Redactor`.
6. **Падение движка — это рестарт с backoff внутри бюджета**, 5 попыток за
   10 минут. Исчерпанный бюджет переводит движок в `failed`, бесконечного цикла нет.

## 4. Что видят другие приложения

Приложения на устройстве могут сканировать loopback-порты. Найдя прокси-порт VPN
клиента, они отправляют через него запрос, узнают адрес сервера и передают его
для блокировки; найдя контроллер, узнают, что клиент запущен. Поэтому:

* **Прокси-порт открывается только тогда, когда без него нельзя:** в режиме
  системного прокси или если пользователь сам включил «прокси для других
  приложений». В режиме tun порта нет вообще. Порт для других приложений можно
  закрыть логином; без логина движок отвечает отказом. Системный прокси логин не
  передаёт, поэтому в режиме системного прокси логин не ставится.
* **Управление без сетевых портов включено по умолчанию**
  (`SessionPlan.network_control_allowed = false`). Контроллер mihomo слушает
  unix-сокет в каталоге с правами 0700 или named pipe со случайным именем.
  Clash API sing-box и метрики Xray бывают только TCP, поэтому в этом режиме их
  не выбирают; причина видна в диагностике.
* Если путь к сокету длиннее 103 байт, сокет создаётся в коротком каталоге во
  временной папке. Каталог принимается, только если это не симлинк, владелец —
  текущий пользователь, а права 0700.

Сквозной тест `TestLocalProxyIsClosedOrLockedOnEveryEngine` проверяет на всех
трёх движках, что без прокси в плане порт не слушается, а с логином запрос без
него не проходит.

Запрет записи экрана (`FLAG_SECURE` на Android,
`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` на Windows) — задача окна
приложения, а не ядра; он делается вместе с интерфейсом.

## 5. Как выбирается движок

`engine.SelectEngine` идёт по `engine.DefaultPreference`
(sing-box, Xray, mihomo) и берёт первый установленный движок, который проводит
каждый протокол и каждую возможность плана (`Capabilities.Missing`). Причины
отказа от остальных движков записываются, и диагностика их показывает. Флаг
`-engine` службы закрепляет один движок; поле `SessionPlan.engine` контракта 1.3
закрепляет движок для одной сессии, если служба не закрепила свой. Фрагментацию
включает `SessionPlan.anti_censorship`.

Возможности, которые план требует явно:

| Возможность плана | mihomo | sing-box | Xray |
| --- | --- | --- | --- |
| tun | да | да | нет: tun-вход есть, автоматических маршрутов нет |
| fake-ip | да | да | нет |
| url-test группа | да | да | да: балансировщик `leastPing` |
| fallback группа | да | нет | нет |
| load-balance группа | да | нет | да: `roundRobin` |
| фрагментация TLS ClientHello | нет | да: `tls.fragment` | да: freedom + `dialerProxy` |
| XHTTP | да | нет | да |
| VLESS Encryption | да | нет | да |
| AmneziaWG | да | нет | нет |
| управление без сетевых портов | да: unix-сокет, named pipe | нет | нет |
| AnyTLS | нет | да | нет |
| Hysteria2 | да | да | да, без obfs |
| TUIC | да | да | нет |

Ячейка «нет» означает «не проверено или не поддерживается», а не «наверняка не
умеет». Возможность попадает в матрицу только после того, как её принял
валидатор движка.

## 6. Особенности каждого движка

**mihomo.** Горячая перезагрузка через `PUT /configs?force=true`: при новом плане
соединения не рвутся. Группы, выбор, задержка и счётчики идут через Clash API.

**sing-box.** Конфигурация пишется в формате 1.12+: DNS-серверы с полем `type`,
действия маршрутизации вместо служебных outbound, WireGuard как endpoint
(outbound удалён в 1.13), geoip и geosite как удалённые rule set от SagerNet
(базы удалены в 1.12). Rule set скачиваются через маршрут по умолчанию, потому что
хосты, которые их раздают, блокируют там же, где пользуются Sora. Перезагрузить
конфигурацию через API sing-box не умеет, поэтому новый план перезапускает движок.
Выбор в группах переживает перезапуск благодаря `cache_file`.

**Xray.** Управляющего API для групп у Xray нет, поэтому:

* выбор в select-группе записывается прямо в таблицу маршрутизации, и новый выбор
  перезапускает Xray, это около 100 мс;
* url-test и load-balance группы становятся балансировщиками, задержку им даёт
  observatory, а читается она из `/debug/vars`;
* `Delay` поднимает второй, короткоживущий Xray, в котором есть только измеряемый
  outbound за SOCKS-входом, и засекает настоящий запрос. Пользовательская
  маршрутизация при этом не трогается;
* теги outbound имеют фиксированную ширину (`o0001`), потому что балансировщик
  выбирает outbound по префиксу тега;
* obfs у Hysteria2 Sora для Xray не рендерит: Xray молча игнорирует незнакомые
  ключи, и сервер подключился бы без обфускации, вместо того чтобы отказать.

`geoip.dat` и `geosite.dat` должны лежать рядом с бинарником Xray, как в
установке Sora.

## 7. Пинг

`registry.Measure` раскладывает серверы по ядрам: каждый сервер уходит в первое
ядро из порядка, которое его проводит, и измеряется настоящим запросом.
mihomo и sing-box поднимают одну короткоживущую копию со всеми своими серверами
и меряют через свой контроллер; Xray поднимает процесс на пачку до 128 серверов,
у каждого свой SOCKS-вход. Сервер, который не проводит ни одно ядро, получает
`ErrNoEngine`, и в режиме «авто» его проверяют подключением. Результаты уходят
клиенту по мере готовности, в каждом указано, каким способом и через какое ядро
он получен.

## 8. Как это проверяется

* `go test ./...` в `core` гоняет рендереры на планах из `enginetest`.
* Если заданы `SORA_MIHOMO_BIN`, `SORA_SINGBOX_BIN` и `SORA_XRAY_BIN`, каждый
  отрендеренный план проходит валидатор своего движка, а живые тесты проводят
  движок через запуск, handshake, группы, выбор, счётчики, новый план и остановку.
  Тест Xray, кроме того, измеряет настоящую задержку через тестер.
* С `SORA_ENGINES_DIR`, где лежат все три движка, тест реестра проверяет выбор
  ядра под план и под пинг, а сквозной тест (`engine/interop`) пропускает
  настоящий HTTP-запрос через каждое ядро и каждый транспорт до локального
  сервера Xray. Неверный UUID обязан не пройти ни через одно ядро, иначе тест
  мог бы засчитать трафик, ушедший мимо прокси.
* mihomo и Xray молча пропускают незнакомые ключи, поэтому имена ключей mihomo
  сверены с тегами, скомпилированными в бинарник v1.19.32.
