# Как устроена Sora

## Части

```
приложение (Flutter, от имени пользователя)
        |
        |  gRPC sora.core.v1: unix-сокет на Linux, именованный канал на Windows
        v
служба sora-core (Go)
        |
        |  конфигурация через stdin, управление через Clash API или сокет
        v
ядра: sing-box, Xray, mihomo (отдельные процессы)
```

**Приложение** показывает состояние и собирает план подключения из выбора пользователя: серверы, группы, маршруты, правила, режим. Само оно в сеть не ходит и прав не требует. Подписки и ключи у приложения не хранятся.

**Служба** работает постоянно. На Linux это пользователь `sora` с возможностями `CAP_NET_ADMIN`, `CAP_NET_BIND_SERVICE` и `CAP_NET_RAW`. На Windows это служба `SoraCore` от имени LocalSystem. Служба хранит подписки, обновляет их по расписанию, запускает ядра, включает kill switch и отдаёт приложению события.

**Ядра** запускаются службой как дочерние процессы. Конфигурация передаётся через stdin, поэтому ключи серверов не попадают ни в аргументы командной строки, ни в файлы.

## Подключение по шагам

1. Приложение отправляет `Connect` с планом и с тем, включён ли kill switch.
2. Служба проверяет план и выбирает ядро. Каждое ядро описано набором возможностей: протоколы, транспорты, группы, TUN. Берётся первое ядро, которое умеет всё, что есть в плане, в порядке sing-box, Xray, mihomo. Если управлять ядром через локальный порт нельзя (по умолчанию так), порядок sing-box, mihomo, Xray. Пользователь может закрепить ядро в настройках.
3. Служба собирает конфигурацию для выбранного ядра и проверяет её самим ядром (`sing-box check`, `xray -test`, `mihomo -t`).
4. Если kill switch включён, служба ставит правила firewall и только потом запускает ядро, так что мимо туннеля ничего не уходит даже пока ядро стартует.
5. В режиме «весь трафик» ядро создаёт адаптер `sora0`. Подключение считается установленным, только когда адаптер действительно поднят.
6. Приложение получает события: состояние, расход трафика, результаты проверки серверов. Если в плане есть fallback-группа, служба раз в пять секунд смотрит, через какой сервер она работает, и сообщает приложению, когда группа ушла на запасной или вернулась на основной.

Если ядро упало, его перезапускает супервизор с растущей паузой, до пяти раз за десять минут. Пока он это делает, приложение показывает «Переподключение». Если попытки кончились, подключение переходит в состояние ошибки, а kill switch остаётся включённым, пока пользователь его не снимет или не отключится.

Раз в две секунды служба смотрит на сетевые интерфейсы. Если сменилась сеть, появился новый адрес или компьютер проснулся, служба закрывает соединения, оставшиеся на старом пути, и программы сразу открывают новые. Ядро без такой возможности (Xray) перезапускается.

## TUN

Адаптер называется `sora0`. Адреса: `172.19.0.1/30` у sing-box, `198.18.0.1/30` у mihomo, `fdfe:dcba:9876::1/126` для IPv6. DNS в этом режиме идёт через туннель по DoH, если пользователь не задал свои серверы.

У Xray на Linux своего управления маршрутами нет, поэтому служба ставит для него правила policy routing сама: таблица 5340 и правила с приоритетом 5335–5339. Трафик самой службы и ядра идёт мимо туннеля по правилу `uidrange`.

На Windows включён `strict_route`: без него Windows отправляет DNS-запросы сразу во все адаптеры, и часть уходит мимо туннеля.

## Kill switch

Linux: таблица `inet sora` в nftables, цепочка на выходе. Пропускается трафик пользователя `sora` (ядра), loopback, адаптер `sora0`, локальные сети и ответы на входящие соединения. Остальное отбрасывается.

Windows: фильтры Windows Filtering Platform в отдельном подуровне с наивысшим весом. Пропускаются ядра и служба, если они запущены от учётной записи службы, loopback, адреса туннеля, локальные сети, DHCP и NDP. Сессия WFP динамическая: если служба упадёт, Windows снимет фильтры сама и не оставит компьютер без сети.

## Системный прокси

В режиме системного прокси ядро открывает локальный прокси на `127.0.0.1`, а приложение прописывает его в настройках пользователя: на Windows через WinINet, в GNOME через `gsettings`, в KDE через `kioslaverc`. Это делает приложение, а не служба: служба работает от другой учётной записи, и её системный прокси не тот, что читают программы пользователя. Прежние настройки сохраняются до изменения и возвращаются, если прокси всё ещё указывает на Sora.

## Хранение

Подписки, их серверы и ключи хранятся в зашифрованном хранилище службы (AES-256-GCM). Ключ хранилища на Windows защищён DPAPI, на Linux лежит в файле, доступном только пользователю `sora`. Каталог данных: `/var/lib/sora` на Linux, `C:\ProgramData\Sora` на Windows. На Windows служба делает каталог владением LocalSystem и закрывает его для остальных.

Журнал служба держит только в памяти, последние записи. На диск он не пишется. Адреса серверов, UUID, пароли и ссылки подписок в журнале маскируются.

Настройки приложения (выбранный сервер, режим, тема) лежат в профиле пользователя.

## Кто может управлять службой

Linux: к сокету `/run/sora/core.sock` пускается процесс из активной локальной сессии (проверяет polkit) или член группы `sora`. Удалённые и неактивные сессии не пускаются.

Windows: к каналу `\\.\pipe\sora-core-v1` пускается процесс из активной сессии, администратор или LocalSystem. Создавать экземпляры этого канала может только служба, а приложение проверяет, что на другом конце процесс LocalSystem.

После подключения приложение получает токен в ответе `Handshake` и передаёт его в остальных вызовах. Любая программа того пользователя, который сидит за компьютером, может управлять его VPN так же, как само приложение. Это та же граница, что у других VPN-клиентов: доступ определяет операционная система по пользователю и сессии.

## Подписки

Загрузка только по `https://`, до пяти редиректов, тело до 16 МБ. Адреса вне интернета (localhost, локальные сети) доступны, только если сама подписка находится там. Редирект снаружи внутрь не выполняется, проверяется адрес после DNS.

Интервал обновления берётся из настроек подписки, иначе из заголовка `profile-update-interval`, иначе раз в сутки. После ошибки служба повторяет загрузку с растущей паузой и оставляет последний рабочий список серверов.

Из JSON-подписок Xray служба удаляет `inbounds`, `reverse`, настройки журнала и статистики и ключи с путями к файлам. Остальное работает как написал провайдер.
