# Аудит безопасности ядра

Дата: **02.10.2026**. Область: `core/errs`, `core/secret`, `core/session`,
`core/engine`, `proto/sora/core/v1`. Метод: чтение кода, запуск тестов и линтера
с той же конфигурацией, что в CI, сборка под все платформы.

## Итог

Критических и высоких находок нет. Ниже — находки, которые были найдены и
устранены в этом же цикле, и находки, которые остаются открытыми с явным
обоснованием.

## Устранено

| № | Находка | Где | Что сделано |
| --- | --- | --- | --- |
| 1 | `x509.HostnameError` без сертификата паникует при печати, то есть привилегированная служба падала бы во время описания ошибки TLS | `errs/classify.go` | ядро строит деталь сама по типу ошибки, не вызывая `Error()` причины |
| 2 | Токен подписки попадал в текст ошибки через `url.Error` | `errs/classify.go` | URL не копируется в деталь вообще: маскировка, которая не убирает токен целиком, хуже, чем отсутствие |
| 3 | Адреса сокетов и имя хоста из `net.OpError` и `net.DNSError` попадали в деталь | `errs/classify.go` | деталь собирается из операции и причины, без адресов |
| 4 | Локальный путь с именем учётной записи попадал в деталь через `fs.PathError` | `errs/classify.go` | путь отбрасывается, остаётся операция и причина |
| 5 | Одна ошибка могла породить несколько строк в журнале | `errs/errs.go` | деталь сворачивается в одну строку |
| 6 | План хранил секреты в памяти после удаления | `secret/store.go` | значение затирается при замене и при удалении, ключ — при закрытии |
| 7 | Неудачная запись оставляла память впереди диска | `secret/store.go` | откат состояния в памяти, тест проверяет расхождение |
| 8 | Файл хранилища мог остаться рядом с секретом после сбоя записи | `secret/file.go` | временный файл удаляется в `defer`, запись атомарная через переименование |
| 9 | Сессия восстанавливала guard дважды после неудачного старта | `session/runner.go` | состояние «guard применён» отслеживается явно |
| 10 | `buf lint` был красным до этого изменения | `proto/buf.yaml` | три правила именования отключены явно, с объяснением; контракт не переименовывается |

## Открыто и принято

| № | Находка | Почему так | Что делается |
| --- | --- | --- | --- |
| 1 | `master.key` на Linux хранится рядом с `secrets.vault` и защищён только правами файла | Служба работает от системной учётной записи; права `0600` и принадлежность каталога службы — это и есть граница. Настольный keyring требует сессии пользователя, а служба её не имеет | Ротация мастер-ключа и перенос в agent-хранилище, когда появится слой службы |
| 2 | Диагностический архив ещё не реализован | Слой `core/diagnostics` не написан | Архив собирается только из уже замаскированных строк, тест проверяет отсутствие секретов в zip |
| 3 | `unsafe` в обвязке DPAPI | API Windows требует указателей на буферы, которые читаются внутри вызова и не сохраняются | Исключение G103 в конфиге линтера с пояснением; каждая точка `unsafe` имеет комментарий |
| 4 | `go test -race` не выполнялся локально | На машине нет `gcc`, а `-race` требует cgo | В CI `go test -race ./...` выполняется на ubuntu; локально гонки не воспроизводятся |
